# 武侠江湖模拟器全面审计

日期：2026-10-04。对象：工作区当前 index.html，包含现有未提交改动。此次不修改游戏源码，不发布。

## 结论

玩家所说的“世界跟着行为发展、别反复说一件事”准确指向当前架构缺口。游戏已经具备前端判定、事实台账、仇家追踪、门派战、榜单更新和剧情去重，但世界大事、NPC生活事件与玩家选择还没有形成完整的状态闭环。

现有推进规则主要靠提示词约束；抗重复主要靠文本相似度和强制插入转场。模型换一种措辞仍能重复旧事，玩家主动连续做同一件事又可能被判成卡住。

建议先修事件状态与结算一致性，再增加玩法。视觉风格清晰，暂不建议大改美术。

## 审计与验证范围

- 阅读当前三个内联脚本，检查世界事件、提示词、记忆、行动结算、对话、比武/门派战衔接、存档、选项与接口实现。
- 阅读 test/run.js、mock.js 与已有专项测试；本次没有把旧测试文件存在视作“已经通过”。
- 在 Node VM 中载入当前脚本，在独立状态中复现下列问题；没有访问玩家存档或调用真实模型。
- 通过 http://127.0.0.1:8966 使用 Codex 应用内浏览器检查样张与角色创建页面，覆盖 1280×720 与 390×844。未调用真实 API，未完成真实长局剧情、战斗流程或全部移动端界面的动态验收。
- 下文标注“复现”的是隔离执行结果；“源码确认”指逻辑可直接定位；“待验证风险”不等同于已复现故障。

## 第一优先级：玩家行为与世界推演

### 1. 世界事件不依据玩家行为挑选，也没有自己的生命周期【源码确认＋复现】

位置：index.html:2426、2483、2684、3411。

WORLD_EVENTS 是 15 条固定文字，pickWorldEvent 只看回合间隔、32%概率和权重。函数没有接收行动，也不筛选玩家地点、季节、已死亡人物、已吞并势力或事件处理结果。冷却针对所有事件，不针对单个事件。

复现：固定随机数后，第100与103回均抽中“武林大会将于近期召开”。没有机制将“已参加、已结束的大会”从待发生事件中退出。开局 world.events 则持续作为“当世大事”注入提示词，常规回合没有事件更新字段。

建议：事件使用稳定 ID，保存参与者、地点、起因、阶段、结果、最后变化时间；阶段至少包括酝酿、发生、升级、结束、搁置。结案后只作为历史事实，不能再作为“近期将发生”。复发必须有新原因和新实例。

### 2. 玩家行为的长期后果没有统一账本【源码确认】

位置：index.html:1162、3265、3388、3439。

部分后果有专门系统，例如仇家、授艺、宿命完成、门派吞并；救人、拒绝邀约、揭露丑闻、公开承诺、放弃追查等仍主要依赖正文与短摘要。缺少“谁因哪次行动改变目标，以及何时作出反应”的统一结构。

建议：每次行动输出已发生的事实变化，并建立因果引用。例如“放过敌手”可能导致感激、回报或重新聚众；由人物性格与利益决定，不应默认每次放人都反噬。近期主要展开玩家行动造成的后果，独立世界事件作为补充。

### 3. 防卡住会强制抢走玩家的行动方向【源码确认＋复现】

位置：index.html:2460、2472、2720、5963。

stuckLevel 取最近4回相邻相似度的最大值；较早两回像，最近两回已明显不同，仍可能触发。NUDGES 会要求离开地点、插入新人、突然发生意外，judgeBlock 将其声明为硬要求。makeJudge 只接收选项，不知道本次自由输入内容。

复现：前两回在华山练不同剑式，后两回已经下山救人并去杭州送信，仍得到85.7%的卡住值。

建议：判断本次目标是否有新进度、代价、信息或决定，结合玩家当前行动。玩家连续练功、审问、疗伤属于合理选择；需要阶段成果或明确耗时，不应该被强制赶走。处理重复时优先完成/推进当前目标。

### 4. 空的未了事项列表不能立即清空旧事项【复现】

位置：index.html:3429。

scene.unresolved 的替换逻辑包在 if(want.length) 内。模型明确返回 [] 时，旧事项仍保留；只有另报 resolvedInfo 或等待过期才能移除。

复现：旧列表为“旧悬案”，提交 scene.unresolved:[] 后，列表仍为“旧悬案”。

建议：区分字段省略与明确空数组。前者保留，后者清空当前关注事项；已完成、放弃、搁置的状态应分别记账，不能全部叫“了结”。

### 5. 推进中的事也可能被按12回期限删除【复现】

位置：index.html:3130、3150。

addUnresolved 已有条目直接返回，不刷新 uAge；ageUnresolved 按最初加入时间判断，而非最后推进时间。

复现：连续12回保留并添加同一追查事项，仍被移出。另一方面，同一件事换措辞又可能生成新条目，重新计龄。

建议：用 ID 识别事项，记录 lastProgressAt；确实无进展时降为背景或搁置。不要凭时间判定已经完成，更不能删除玩家仍在追的主线。

### 6. NPC生活事件与风闻多为展示文字【源码确认＋隔离验证】

位置：index.html:2799、3265、5376。

npcEvents、rumors 被显示在章节里，但 applyTurn 没有将它们统一写入人物人生状态和世界事件状态。对应变化需要模型另外正确填写 npcUpdates 等字段。若婚嫁、死亡或结仇只出现在琐记里，就可能没有结构化后果；正文仍保存在章节，但后续提示并不会固定重取这些附加栏。

建议：生活事件也要有参与者、类型、结果和事实引用；重要变化由引擎落账并核对。风闻区分已证实、未证实、过时，避免把传闻永久当真，也避免重要事件从摘要里消失。

### 7. 带人名的旧选项可以不断回流【复现】

位置：index.html:5913、5924。

anchored 选项绕过“刚做过”和“连续出现三回”的检查。人物名、势力名、部分宿命文字都会成为保留依据。

复现：玩家连续两回“找岳师伯打听旧案”，同名选项仍保留。未选的线索可以保留，但已经完成的动作应该产生下一步，而非无限保留。

建议：选项挂到目标 ID 与阶段；区分未选、已做、已失效、可重复活动。填充选项根据当前场景和目标生成，避免总塞“去邻县”“去茶楼”。

### 8. 掌握信息被自动当成待办任务【源码确认】

位置：index.html:4848。

对话 effects.info 直接 addUnresolved。玩家知道一条消息，不代表想追这条消息；与“只挂玩家打算去管的事”的提示词原则冲突。

建议：知识、传闻、承诺、任务、当前关注分别保存。询问信息不自动接任务；明确接受或主动调查才变成关注事项。

## 第二优先级：结算、恢复与人物一致性

### 9. 时间尺度粗，短行动也至少一个月【源码确认＋复现】

位置：index.html:1350、2749、5888、5963。

普通行动由 optMonths 至少给1个月，自由输入无法让“问一句/等一天/闭关一年”决定耗时；对话余波另走0个月的特例。0个月文本又被 judgeBlock 的 judge.months||1 在局部表达中当作1处理，虽然对话分支避免展示常规时间。

复现：optMonths({months:0}) 返回1；advanceTime(0.5) 返回历时0.5，实际 S.months 增加1。目前主流程主要传整数，后者属于扩展时间精度前必须修正的边界问题。

建议：统一用天或明确整数时间单位。长期行为可以简洁概述，按节点推进世界；即时行为不要凭空扣一月生活费。时间结算与叙事时间使用同一个结果。

### 10. 世界变化在正文生成之后结算【源码确认】

位置：index.html:3443、6067、6083。

提示词读取回合前状态，applyTurn 才推进时间、老化、病故、门派事务和榜单变动。这些消息通常下一回才进模型；本回合正文可能仍把将发生改变的人物当成正常状态。

建议：明确回合内顺序：行动判定、时间推进与环境变化、叙事生成、最终提交。长闭关期间发生的死亡/势力变化应作为同次叙事输入，避免下一回才补说。不能通过提前永久落账来引入重试重复结算。

### 11. 合法JSON不代表有效回合，缺少完整校验【源码确认＋复现】

位置：index.html:3038、3078、6067。

parseJSONLoose/repairJSON 可以修补截断回复；llmJSON 主要检查能否解析，不核对 narrative、字段类型、数值合法性或引用人物。提示词要求“最多2个新NPC”，applyTurn 没有相同硬上限。提示词要求实际推进，也没有回合后验证。

复现：只有 summary、没有 narrative 的对象可通过解析。不能把 JSON 修复成功直接视为有效剧情。

建议：提交前验证必需字段、对象引用、数值范围、阶段变化与引擎判定；发现不一致只修正本次输出，成功后一次提交。避免正文说成功、面板记失败，或正文死亡、引擎救活后仅在附栏更正。

### 12. 战后叙事中断恢复会丢失门派战上下文【源码确认】

位置：index.html:4461、6065、6381。

runTurn 支持 extra.warData，但 pending 只存 action、judge、duelData；重载继续只恢复 duelData。afterWarDuel 在叙事前已经结算并清空 war，若此时关闭页面，恢复时可能按普通回合叙述，缺少该场战争实录。

建议：pending 保存回合类型、完整战后结果与结算 ID。已经结算的战争只补正文，不重算胜负和奖励。参悟秘籍也有“先结算再写正文”路径，应一起检查。

### 13. 回合提交不是完整事务【待验证风险，源码路径明确】

位置：index.html:6072、6108。

pending 在 applyTurn 前清空；applyTurn 逐项直接修改 S。若后面字段类型异常、渲染异常等发生错误，catch 提供重试，状态可能已部分或全部变化。重试不具备统一幂等 ID，也没有完整回滚。

建议：在克隆状态中校验和结算，再原子替换主状态；正文与存档属于同一个提交结果。已提交但显示失败只能重画/补记，不重新扣钱或加奖励。

### 14. 同一人物在名录与榜单中分别老化、判死亡【源码确认；风险需专项复现】

位置：index.html:1199、1262。

npcYearTick 分别遍历 NPC 和榜单人物，即使二者是同一个人也分别运行成长、衰老、死亡概率；rankRefresh 才做部分同步。不能称为“年龄必然加两岁”：此次复现两份年龄都是40→41。实际风险是两份随机判定与面板分歧，人物字段缺少统一权威来源。

建议：统一人物实体 ID，名录、榜单、势力首领只引用它。死亡、武功、年龄在同一实体上只更新一次。

### 15. 人物出现与交往缺少位置和在场约束【源码确认】

位置：index.html:2640、3384、4860。

相关人物筛选主要看好感、关系、最近回合；openConvo 可以直接与任意存活人物交谈，没有旅行或同地检查。npcUpdates 一律更新 lastSeen，即使是远方人物后台变化。

建议：为人物保存已知位置和当前在场列表；远方交互用书信、派人或旅行。后台变化不等于与主角见面。“重要人物”也不等于“当前就在身边”。随心所欲档可保留便利，但叙事仍要解释来由。

### 16. 背景压缩异步完成后使用全局 S【待验证风险】

位置：index.html:2930、6110。

foldHistoryInner 在 await 前取旧 history，返回后向当前 S 写 volumes 并切片当前 history。若期间另起一局或读其他存档，可能把上一局摘要带入新局。摘要过多时合并直接截取前600/400字，较新的事实可能被截掉。

建议：绑定 runId、状态版本与取样范围，写回前核对；压缩只处理当前局的那一批行。重要事实独立保存，检索时按当前事件相关性取用。ledger 本身只有80/30条，不是无限永久记忆。

### 17. 对话等待期间告辞存在忙碌状态竞态【待验证风险】

位置：index.html:4889、4928。

对话请求允许等待中告辞；旧请求 finally 无条件 busy=false。若玩家告辞后开始另一项请求，旧请求结束可能提前解除新任务的忙碌锁。告辞时 !busy 条件也可能导致谈话余波没有生成。

建议：每次请求使用独立 token 与取消机制；只有当前请求能释放对应锁。告辞后保证已完成效果有摘要与可继续选项，避免旧请求干扰新回合。

## 第三优先级：体验、性能与维护

### 18. 手机阅读与长表单体验

位置：index.html:5、6572。浏览器观察：390×844 创建界面存在弹窗、头像区、出身区多层滚动。

建议：保留纸墨风格，减少嵌套滚动；开始按钮更容易到达，输入区处理软键盘与安全区。当前禁止双指/双击缩放，会影响长篇阅读，建议允许放大并提供字号设置。桌面样张检查未见横向溢出，但其他面板与实际长局仍需单独验收。

### 19. 世界面板缺少玩家可理解的因果展示

位置：index.html:5268。

当前当世大事为平铺文字。建议显示“什么变了、为什么变、下一步何时发生、你能如何介入”；区分当前事件、待办、已结束记录。玩家应看得出自己做的事改变了谁的态度或局势。

### 20. 请求与上下文成本

位置：index.html:1171、2672、2975。

长记忆带很多摘要、人物、榜单和台账，远方/已亡人物数量也会增长。接口默认 max_tokens 12000，温度1.05，超时180秒按流式内容刷新，持续零碎输出可能一直等待。正文只要求250—500字，却还携带大量系统规则与输出字段。

建议：先按事件、人物、地点检索相关上下文，再限预算；叙事和事实提取可有不同约束。增加取消、重试状态和总时长限制。模型参数调整只能辅助，无法代替事件状态管理。

### 21. 规则宣传和实际判定边界不完全一致

位置：index.html:2731、4895、6604。

样张说明称“成败不归模型管”，但自由输入非预设判定、对话 attempt 的成败仍有模型参与裁定。建议明确哪些由引擎计算，哪些由模型评估；对可计算的数值判定统一在引擎复核，避免更换模型后规则漂移。

### 22. 单文件维护与测试覆盖

index.html 集成大量界面、规则、网络和存档逻辑。已有测试对数值和玩法有积累，但当前抗重复测试主要确认“相似就触发干预”，未证明“玩家连续行动合理推进且不被打断”。

建议先补用户目标场景的回归，再渐进拆分事件、记忆、判定、存档、渲染模块，保持发布入口兼容。无需一开始重写整个游戏。

## 建议的施工顺序

1. 修空列表清除、已完成选项回流、误判卡住、活跃事项过期；补回合校验、门派战 pending 与提交幂等性。
2. 建统一事件账本与玩家行动后果；将世界大事从固定文字改成阶段状态；结案归档，复发要求新原因。
3. 统一时间、人物实体、位置与后台推演，让NPC与势力自主行动，也受玩家影响。
4. 再做相关记忆检索、世界面板、手机阅读和代码拆分。

## 世界推演应该呈现的行为示例

玩家接连追查镖银：第一次确认失镖路线，第二次辨出内应，第三次决定揭发或交易。可以连续调查同一案件，但每回都有新信息、代价或决定。

玩家决定不追：案件从“当前关注”退出；镖局与劫匪仍可在后台行动，日后出现新后果时再提示。不要每回强行让玩家继续破案。

玩家灭掉黑风寨：寨主、成员、地盘与关联悬赏改变；事件结束。若残党再起，要有明确幸存者、重建过程和新时间，不能继续说原寨“近日猖獗”。

玩家闭关半年：修炼成果可以概述；江湖按半年经过更新，重要人物变故与玩家曾作出的承诺一起结算。不因练功文字相似就突然把玩家拉去另一个城。

## 下一轮验收合同

- 同一事件完成后连续10回不再作为待发生大事；若再发生，能说明新起因。
- 连续5回同一合理活动，保持玩家方向，记录阶段进展，不强制转场或塞陌生人。
- 明确放弃、已经完成、空未了列表分别正确处理；仍在推进的目标不被12回期限删掉。
- 已做选项转成下一步；未做但有效的钩子可保留；不存在过期人物/势力引用。
- 长闭关后人物、地点、势力、日期和正文一致。
- 主角行为导致至少一个可查的后果，后果能引用原因；无影响的日常行动允许世界平静，不强迫大事件。
- 普通回合、对话、比武、门派战、参悟均测试请求失败与重载；奖励、损失、时间只结算一次。
- 新局/换档不会接收旧请求或旧摘要；异常模型字段不破坏主存档。
- 实际 API 做至少20—30回多分支长局验证，结合人工检查因果、重复和玩家意图；Mock测试不能代替模型叙事验收。

此次没有验证真实模型的重复发生率，也不把设计建议当作已完成修改。
